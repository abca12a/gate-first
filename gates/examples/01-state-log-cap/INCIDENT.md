# 事故复盘 01：打了两周警告仍膨胀到 569 行 / 104 KB

## 事故时间线与实测读数

- **2026-09-17**：为解决交接文档越写越长的问题，团队在三处核心文档（全局协作规则、仓库 `AGENTS.md`、`README.md`）同时写明硬规矩：`docs/STATE.md` 的「`## 当前动作`」节只准保留进行中与下一步，上限 **120 行**，历史过程移入 `docs/archive/`。同时在开工读取脚本 `next.mjs` 中加入了超限黄色警告。
- **隐患埋入**：`next.mjs` 的职责是开工时把「当前动作」打印出来供人和 Agent 阅读，因此超限时只向终端打印警告，**进程退出码依然是 `0`**。
- **2026-09-25 爆发**：短短 8 天、数十轮多会话迭代后，实测 `docs/STATE.md` 的「`## 当前动作`」膨胀到 **569 行（原定上限的 4.74 倍）**，`npm run next` 每次开工向模型上下文直接倾倒 **104 KB** 历史流水账——而代码照跑、单测全绿、评审照过，**全程没有任何一个环节报错**。

## 根因剖析

1. **「只提醒不失败」的约束等于没有约束**：对目标导向的编码 Agent 而言，只要命令返回 `exit 0`，警告文本就会在注意力竞争中被当作背景噪音忽略；下一轮 Agent 看到前人留下的几百行日志，还会顺着同一格式继续往后追加（破窗效应）。
2. **读取入口与门禁入口不能混为一谈**：如果直接把 `next.mjs` 改成超限 `exit 1`，那么一旦超标，连开工查看当前状态的入口本身都无法工作。
3. **双份常量必然漂移**：拆出独立门禁脚本后，若两边各自硬编码 `120`，日后调整阈值极易出现「读取器报超限、门禁判通过」的分裂假绿。

## 门禁设计与落地

1. **抽出单一阈值源 [`state-section.mjs`](state-section.mjs)**：统一导出 `HEADING = '## 当前动作'`、`LINE_LIMIT = 120`、`readCurrentAction()` 与 `currentActionBody()`。
2. **新增阻断式门禁 [`check-state-log.mjs`](check-state-log.mjs)**：
   - 找不到 `## 当前动作` 节 → `exit 1`（防止把标题改名绕过检查）；
   - 剔除 `> ` 说明引用块后正文为空 → `exit 1`（「空」不等于「没有下一步」）；
   - 行数 `> 120` → `exit 1`，并在报错中直接打印当前行数、上限及归档落点（`docs/archive/`）；
   - 后续章节（下一个 `## ` 起）不计入本节行数，防止其他合法章节增长引发误报。
3. **阳性对照 [`test-positive-control.mjs`](test-positive-control.mjs)**：自动验证 `120` 行放行、`121` 行阻断、缺节阻断、纯引用块阻断、后续长章节不误伤，以及源码级单一常量源一致性断言。
