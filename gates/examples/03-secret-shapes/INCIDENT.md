# 事故复盘 03：未 `git add` 新文件漏扫盲区与双向过期白名单

## 为什么「仓库里没有明文密钥」必须做成门禁

「明文凭据没有进版本库」是一个典型的**否定命题**。一次性全仓扫描只能证明**当天那一刻**是干净的，而密钥进仓的真实路径往往是：
- 排障时把真实接口响应粘进代码注释；
- 在提示词或调试文档里顺手留了一段真实 Bearer Token；
- 为单测写 mock 时直接从生产网络面板复制了响应头。

这些动作不会破坏任何产品功能，编译、单测与人工阅读全部照常通过。唯一能持续守住否定命题的办法，是把它变成每次 `git commit` 必跑的形状扫描。

## 真实踩过的两个门禁盲区

### 盲区 1：只用默认 `git ls-files` 漏掉尚未 `git add` 的新建文件

- **踩坑现场**：初版门禁使用 `git ls-files` 获取受控文本文件列表。做阳性对照时，往一个刚新建、尚未执行 `git add` 的文件里写入测试假密钥，结果门禁**根本没报发现凭据**（反而报了别处的白名单统计异常）——因为默认 `git ls-files` 只列出暂存区索引（`--cached`），对工作区新建未跟踪文件完全失明！而「刚写完脚本或配置、还没暂存」恰恰是最容易残留真实凭据的时刻。
- **修法**：扫描范围必须改用：
  ```bash
  git ls-files -z --cached --others --exclude-standard
  ```
  既把未暂存的新文件纳入拦截范围，又自动沿用 `.gitignore` 排除 `node_modules/`、`dist/`、`.tmp/` 等本地目录。

### 盲区 2：没有理由与过期反查的白名单，终将退化成藏污纳垢的垃圾桶

- **机制设计**：
  1. **严选高信噪比形状**：只拦截几乎不可能是普通文本的凭据结构（如 `sk-` 长串、`Bearer ` 长令牌、三段式 `eyJ` JWT、`ghp_` GitHub 令牌、`AIza` Google 密钥、PEM 私钥头），刻意不收「任意 32 位十六进制串」（文档中的 commit SHA 和 UUID 会瞬间撑爆白名单，导致狼来了效应）。
  2. **强制填写豁免理由**：白名单对象的键为命中的原文，值必须是**非空理由字符串**（说明来自哪个测试金丝雀、为何不是真密钥）；空理由直接判失败。
  3. **双向过期反查（Stale Allowlist Check）**：扫描结束后反向核对白名单中的每一项是否仍在仓库中出现。若某条测试桩已被删改、白名单却未同步移除，门禁立即报「白名单过期」并 **`exit 1`**，杜绝死条目长期堆积。
