# 推送 GitHub + 核对 CI

**核心分界：任务不是「把提交推上去」，是「远端门禁的结论是什么」。**

这条被真实辜负过（2026-09-19）：推完 58 个提交就报告「推送完成」，那次 CI 实际是
**failure**，一个多小时后才发现。`push` 成功 ≠ CI 通过。

## 推送前先看授权

推送、部署前先读项目状态入口的「当前授权」记录（允许、禁止、有效期），并在回报里引用。

- 有记录且本次在范围内：直接执行。
- 无记录或超出范围：先给用户一份确认单并等确认——仓库、目标提交（完整 SHA 与原远端 SHA）、包含的改动、影响面、部署方式、需验项、回滚方式。没确认不推。

## 第 0 步：推的是**产物**时，先确认产物是新的

推 `main`（源码）不涉及这条。**发布 / 部署 / 打包分支推的是构建产物**，那要多一道前置：

**构建的判据是日志里的 `✓ built in` 与退出码，不是「命令跑完了」。** 2026-09-20 真实踩到：
`tsc -b` 过了、构建器在**清空输出目录**那一步被环境的安全策略拦下（那一层拒绝批量删除：
`dist/assets` 下 136 个文件 > 阈值 50），**构建终止而产物原样保留**。
于是「改源码 → 构建 → 打包 → 发布」做了两轮，线上一点没变 —— 而且每一步看上去都成功了。

构建因安全策略拒绝清理而失败时，保留错误和旧产物，报告阻塞；不通过移动输出目录规避拒绝。获得可执行的清理授权或环境调整后再构建，并重新验证退出码与产物。

**构建产物还要过一遍「不该存在的东西」，入口与判据以项目规则文件（AGENTS.md、CLAUDE.md 等）声明的产物门禁为准**（实例：查 `dist/` 里有没有 `.map`
以及内联 `sourceMappingURL`）—— 因为 `/assets/*` 是 `immutable` / 一年，泄漏出去的源码删不掉。
⚠️ **Windows 上不能仅凭上传成功把门禁失败判为误报**：历史上 `sentryVitePlugin` 的
`filesToDeleteAfterUpload` 在 Windows 上不生效（CI 的 Linux runner 上生效 —— 同一次发布的 CI 日志里
这条门禁扫 155 个文件后**通过**），而构建日志照样写着 `Successfully uploaded source maps to Sentry`。
判据：`ls dist/assets/*.map | wc -l` 必须为 0；本机不为 0 且日志里有那句 `Successfully uploaded`
⇒ 仅说明上传与删除是不同阶段。若实际待发布目录仍有 `.map`，就是有效阻断，不能发布该目录。按当前项目的安全清理流程解决并复验；不要照搬历史平台结论。

**「线上没变」的排查三步 —— 先量，别读代码：**

```bash
# ① 线上入口 chunk 名 vs 本地
curl -s https://<域名>/ | grep -o 'assets/index-[A-Za-z0-9_-]*\.js'
grep -o 'assets/index-[A-Za-z0-9_-]*\.js' dist/index.html
# ② 这条发布通道最近一次 run 的时间戳（是不是真的刚发过）
gh run list --repo <owner>/<repo> --limit 3
# ③ 产物里的特征字符串：本轮该消失的 / 该保留的各数一次
grep -c "<本轮删掉的那句话>" dist/assets/<chunk>.js
```

判据是 **线上入口名 == 本地入口名** —— **但这条判据有一个前提：两边用同一套构建期注入。**

⚠️ **前提不成立时，这条判据会给出错误结论**（2026-09-22 实测，差点误判成「线上跑的不是这份代码」）：
本地构建若没注入构建期 secret（如 `SENTRY_AUTH_TOKEN`），`sentryVitePlugin` 就不给 chunk 注入
`_sentryDebugIds` ⇒ **内容变了、内容寻址的名字全变**：本地 `index-DBeiFAMW.js` / 534220 B
vs 线上 `index-DEI754ru.js` / 534607 B。补上 token 重建后立刻**同名同 sha256**。

```bash
# 先分清是「本地少了注入」还是「本地产物是旧的」
curl -s https://<域名>/assets/<线上入口 chunk> | grep -c _sentryDebugIds   # 线上：1
grep -c _sentryDebugIds dist/assets/<本地入口 chunk>                        # 本地：0 ⇒ 别下结论，补注入重建
```

所以「线上入口名 ≠ 本地入口名」要**先分三档**：① 本地没注入构建期 secret（本条）⇒ 补上重建；
② 本地产物是旧的 ⇒ 查构建日志里有没有 `✓ built in`（见上）；③ 注入一致、产物还不同 ⇒ 才是
「构建或打包有问题，不是部署问题」。**别一上来就怀疑 CDN 缓存**（HTML 不缓存时，刷新不是变量）。

**发布后的字节级验收**（本机就能做）：线上 HTML 与本地产物的 sha256 相同 + 入口 chunk 三方一致 +
**本轮改动所在分片的 sha256 逐字节相同**（见第 3.5 步：别只比入口名，也别靠特征字符串计数）。

⚠️ **比对前先取「当前入口 chunk 里列出的分片名」，别用上一轮的旧名。** `/assets/*` 是 `immutable` / 一年
（常带「上一部署回退」绑定），**旧名字永远返回 200** —— 拿旧名字 curl 到的是**旧部署**的内容，
会把「分片名全换」误读成「分片内容没变」。2026-09-22 就被它骗过一次。另外：**构建期 `release` = HEAD 短 sha
若被注入每一个 chunk**，则**每多一个提交，全部 chunk 名都会换** ——
「本地入口名 == 线上入口名」这条判据**只在同一 commit 下成立**（同一次实测：只多一个 docs 提交，
118 个分片名全换，代码一个字节没改）。

⚠️ **HTML 的 sha256「相同」是强证据，但「不等」不一定是缺陷**：本机 `core.autocrlf=true` 会把仓内以 LF
存的纯文本检成 CRLF，vite 原样搬进 `dist/` ⇒ 同一 commit 在两台机器上 `index.html` 差「行数」个字节
（2026-09-22 实测本地 3096 B / 线上 3034 B，而**入口 chunk 与分片逐字节相同**）。判据：字节数差是否恰等于
行数、或 `git ls-files --eol index.html` 是否报 `w/crlf`。**别拿 HTML 的 sha256 不等直接判「部署错了」。**

做完再更新发布记录 —— 但先看那份记录记的是哪一版（覆盖式的 JSON 可能停在更早的一次，见第 3.5 步）。

⚠️ **「推 main 即部署」的通道下，记发布记录的那个 docs-only 提交本身也会触发一次部署**（内容相同、
`production` id 前进一位）—— 2026-09-22 实测，若发布脚本里**没有**「内容相同就跳过」的守卫，会有两个后果：
① 记录里**要以产物内容（入口 chunk 的 sha256）为主键，deployment id 只作辅助**，否则记录写完就已过期；
② 每次补记都是一次生产动作，**推送前要跟负责人说清**。

⚠️ **路径过滤落地后可消除此开销**：在 CI 中落地第 3.6 步的路径过滤（`changes` job，排除
`docs/**` / `*.md` / `deploy/production-release.json`）⇒ **补记发布记录是零成本的，不会再产一次部署**。
判据：补记那次 run 的 `gh run view <id> --json jobs` 里 `release` 为 **`skipped`**（不是 `success`）。
**动笔前先确认目标仓有这套过滤** —— 没有的话上面两个后果仍然成立。
（2026-09-25 实测：含 `src/**` 的提交 `changes` 判 `code=true`、`release` 照常 `success`。
**2026-09-27 把另一半也测了**：只改 `docs/reference/FRONTEND-CUTOVER.md` 的提交 `913562b`
（run `36311594040`）⇒ `changes` / `test(1..4)` / `static` 六个 job 全 `success`，
**`release` = `skipped`**，而**总结论仍是 `success`** —— 所以「发布了」和「跳过了」在
`conclusion` 上长得一模一样，**必须读 `--json jobs`**，这条现在是实测过的、不再是推断。
⇒ **补记发布记录（纯文档提交）确实零成本**，可以放心用来追平 `production-release.json`。）

**打包与入库核对优先用项目已有的脚本，别每次现写一次性脚本** —— 没有就补一个，并把它加进项目声明的门禁入口。这类步骤每次发布都要做，留在 `.tmp/` 里的一次性脚本
下次还得重写一遍；变成仓库里的命令才是真的省事。**补脚本时记得先跑阳性对照**（改坏一条，
看它是否真的报错并退出码非 0）。

## 第 1 步：推送前（不可省）

```bash
git status --short                       # 工作区是否干净
git status -sb | head -3                 # ahead 几个
git rev-list --left-right --count origin/main...HEAD
git log --oneline origin/main..HEAD      # 待推的是哪些提交
```

- **工作区有未提交改动时先问清楚**：那些改动是本次范围吗？`git status` 干净而用户说
  「我改了东西」时，改动往往已被别的 agent 提交了 —— **不要假设有未提交改动**，
  真正待办的常常只有 push。
- **反过来也别假设「已经提交了」**（2026-09-26 实测）：会话摘要或记忆里写「未推送、未部署」
  时，读起来像「已提交、只差推」，而实际可能**连提交都还没做** —— 那次 15 个改动文件全在
  工作区、一个都没提交，且 HEAD 正好等于 main（`git rev-list --left-right --count main...HEAD`
  是 `0 0`，看着「没有待推的东西」）。**推送任务的第一条命令永远是 `git status --porcelain`**，
  它比任何摘要都硬；待推范围要靠「工作区改动 + 未推提交」两处一起看。
- **`npm run check:quick` 在干净工作树上可能只跑静态门禁、不跑单测，而退出码仍是 0**（2026-09-26 实测）：
  若门禁脚本按「有没有**可关联的源码改动**」决定范围 —— 改动**已提交** ⇒ 工作树干净 ⇒ 只跑那批静态门禁
  （36.9s）并打印「未运行任何单测 —— 这不等于本轮业务已验收」。**要跑单测必须显式传全量参数**
  （如 `npm run check:quick -- --all`，实测 175 文件 / 2273 测试，113.5s）。所以「快速检查过了」
  在**提交之后不等于单测过了** —— 又一个「绿灯说的不是它量到的东西」，别把警告读成噪音。
- **仓库是 PUBLIC 时，推上去收不回来。** 推前跑一次凭据门禁：
  `npm run check:secrets`（查 `sk-…` / `Bearer …` / JWT 等凭据形状）。
  别的项目按它自己的凭据门禁跑。
- 提交信息里的**否定式断言**（「已无调用方」「已无引用」）必须有一次机械 grep 支撑 ——
  这类句子写错了没人会报错。
