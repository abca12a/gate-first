# 协作、隔离与验收

本技能处理“一个任务由谁负责、何时才需要分工、怎样留下可用证据”。普通执行能力以当前宿主实际提供的工具为准。

写代码、改配置、跑验证或操作 Git 时，先读[工程规范](references/engineering.md)。给新项目装协作骨架、门禁与交接模板时，读[脚手架](references/scaffold.md)并运行 `scripts/init-project.mjs`。

## 结果与一个负责人

- 一个负责人做到交付、高歧义先交代表成果、不降标准这三条红线见全局规则「执行责任」，这里不复述；本技能只补怎样落地。
- 开工前写清可观察结果、失败信号、关键待核假设及原证据入口；短任务可内联，复杂或委派任务使用[结果工单](templates/AGENT-TASK-TEMPLATE.md)。

## 规模、预算与停止

- 按真实工作量调整预算，不设“多少分钟必须换会话”或固定工具步数。长任务写实际时间/调用预算、绝对截止和停止条件；用户已给优先。
- 达到验收、授权到期、预算耗尽、连续无新证据或出现需用户决定的实质歧义时停止并留下检查点。
- 只有用户明确要求持续执行时，才使用当前宿主的持续执行或定时能力；普通长任务在连续上下文里推进。

## 何时分工

先按清单判断，不按“要写代码、要构建、要验收”机械换人。

派（满足任一）：

- 两个以上互不重叠的写目录，且同一轮都要交付，并行收益大于协调成本。
- 高风险独立审查：发布前、安全、支付、权限、数据迁移改动、跨仓库契约改动。
- 需要外部证据而主流程不能停：查文档、跑长验证（如真实浏览器交互清单）、等外部回执。
- 负责人自己证明不了对错的产出：对外文案、价格或金额换算、迁移脚本。交给不带本次上下文的审查者，只给需求原文与产出。

不派：

- 单文件或单目录的连续改动；任务书比改动本身还长。
- 需要共享上下文做取舍的设计、集成、验收判断。
- 提交点的门禁：由执行者在提交时跑一次并回传原始输出；主导只复核证据，不亲自运行。不阻塞主流程的长验证不在此列。

派发前父会话先完成力所能及的检索，任务书写清已核实的事实、文件路径、边界和验收；子代理不重复检索。检索为空先分清“没查到”和“没执行”。子代理默认不提交、不跑全量门禁；验证范围写进任务书，全量门禁由执行者在提交点跑一次。

## 宿主与异步协作

- 先核对当前宿主真实存在的派工、任务记账、消息、状态和权限接口，不把别家接口写进工单。真正独立的子任务派出后，主流程继续做不依赖结果的工作，用异步通知或非阻塞查询接续，不做让用户无法插话的阻塞等待。
- 能力缺失时由负责人串行完成或如实报告，不冒充已委派、已异步或已验收。宿主映射与交接细节见[薄宿主适配](references/host-adapters.md)。

## 多会话协作

多个会话可能同时改同一仓库。开工时先声明本次工作区与文件范围，并核对 `git status` 与最近提交；需要并行时按目录或文件切开，不靠自觉。

- 写入分两档：同一目录同一时刻只有一个写者，其他会话只读（不改文件、不跑会改文件的命令）；需要并行写时每个会话各开 worktree 与分支，各自提交、各自过门禁，由负责人合并，见[worktree 隔离](references/worktree.md)。不用“能改不能提交”的口头提交权：没人看得出谁持有，门禁检查整个工作区，会把别人的半成品一起算进来。
- 交接：离开未完成任务前，把当前状态、已改文件、未决项写进项目状态入口或原任务记录，不依赖聊天上下文。
- 冲突：发现别人改过同一文件，先读对方改动并以它为新基线；不覆盖、不回退、不顺手清理。
- 共享记忆：同一事实只写一次；写入前按标题与描述查重，已有就更新原条目，不新建。子代理/执行者只回报证据，不直接写跨会话共享记忆，由主导者统一决定是否沉淀；两个会话同时写同一条时，后写者合并进先写者。
- 门禁：各会话的提交都走同一 hook；谁提交谁对当次绿负责，不拿别人会话的旧证据当自己的。工作区里有别人未提交的改动时不提交，先交接或换 worktree。

## 修改与隔离

- 修改前核对分支、完整基线、status、diff、现有改动、并行任务和授权。用户及其他会话的内容原样保留，不靠清理工作区解决问题。只读任务可共享目录，但不运行会改变文件或外部状态的命令。
- 单个执行者可在明确授权的主目录顺序修改。只有多个写者并行、需要隔离风险，或任务明确要求独立分支时，才建立 worktree；检查入口、隔离边界与合并前动作见[worktree 隔离](references/worktree.md)。

## 检查与失败

- 门禁唯一执行点、失败必须修复、不得用恒零检查或删测试制造绿色，见全局规则「检查与交付」。
- 先做与风险最相关的针对性检查，再运行项目既有最终 hook/入口。代码和环境判据没变时复用已有证据；修正后重试对应检查。
- 同一事实只核一次，证据落盘一次；后续引用不重核，除非证据可能已过期。
- 测试质量、失败分类与验证分层的判据见[工程规范](references/engineering.md)。

## 交付与证据

- 按[证据回报](templates/EVIDENCE-REPORT.md)先给用户判断摘要，再附实际命令、退出码、关键输出、diff 和证据范围。
- 只报完成项、实质风险、预计延误和需决定项；准备过程旁白不转发。
- 明确区分已验证、待核对、未执行；有未覆盖项时不用“全部完成”“收口”概括。
- 授权写进项目现有状态入口或原授权位置。凭据不进入日志；外部写入结果不明时先查回执，不重放。
- 历史事故和旧证据留在原历史位置，不因新规则重写事实。

## 共享源与生效边界

- 本技能建议由多宿主共享实体分发器（如 Magpie 或自定义同步脚本）统一管理，各宿主入口应指向同一目录。修改前核对实体、链接、来源索引、所有消费者和实际加载入口；只改限定资产，不因能运行全库同步就扩大范围。
- 文件入口更新只证明源和消费者同步；宿主 catalog、新会话实际加载和真实任务行为仍需分别验证。本机更新不代表其它电脑或网络远端已同步。
