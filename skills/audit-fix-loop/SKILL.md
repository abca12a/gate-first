# 审计项修复循环

用户丢来一段审计报告（不管是人写的、另一个 AI 写的、还是 CI 输出的），要求「按 P0 → P1 → P2 修完」时，
**不要直接从第一条开始改代码**。这份流程的每一步都是在挡一种具体的失败。

具体事故实例、实测读数和症状表见 [CASE-NOTES.md](CASE-NOTES.md)，按需查阅，不默认通读。

## 第 0 步：核对结论，不盲信

审计报告是**别人的判断**，不是事实。逐条打开它点名的文件与行号，确认：

1. 行号处的代码**真的**是它描述的样子（报告常基于旧版本，行号会漂）。
2. 描述的行为**真的是缺陷**——还是「画板多画了 / 实现少了 / 这是有意设计」。
   判据是**这个项目里同类东西本来怎么做**，先去找那个先例。
3. 有没有**同族页面存在同一缺陷但报告没列**。修不修要判断，但**报告里必须写出来**，
   不能悄悄扩大范围也不装作没看见。
4. **前提本身成不成立。** 报告常从一个代码事实推演出一个用户可见的后果，而中间那步可能是错的。
   三种形状（完整实例见 CASE-NOTES 第 1 节）：
   - **推演的行为不存在**：它说的缺陷早在文案或实现里处理过了 —— 按事实记账，不把它写进交付。
   - **交互推演被真实浏览器证伪**：「点一下会怎样」这类断言只有真浏览器算证据；证伪就补一条回归测试钉住判据，**不改代码**。
   - **建议的修复没有落点**：要加的就是新产品面 —— 如实写「建议无落点，待产品决定」，不为让报告好看而发明入口。
5. **已有实现里可能已经处理过一半。** 先读全，再决定补什么 —— 否则会重写一遍已经对的东西。

把核对结果整理成任务清单（一条任务 = 一个可独立验证的修复单元），再动手。

## 第 1 步：先写最小回归测试

**测试先于实现。** 而且必须是**最小**的——只钉住这一个缺陷的那一句话，不要顺手把整个模块测一遍。

- 测试的**失败信息必须直接描述症状**，不是「期望 true 得到 false」。
- 数**出口**，不数体积：渲染循环的判据是**查询次数**；文档膨胀的判据是**消费它的那条命令吐出多少行**。
- 需要 UI 层验证的（键盘、无障碍角色、表单状态），用组件测试；不要为了省事只测纯函数。

### 两类缺陷的判据要特别设计

**「出口」类**（结果不明时用户只能手动刷新、指标看不到完整列表）：

- **出口必须对得上对账面。** 不同业务的出口不是同一个页面，机械照抄会得到「人人点得动、点完什么也看不到」的按钮。
- **「有出口」与「出口真的通」在界面上长得一样** → 用例要数**请求数**，不能只断言按钮存在。
- **说明与出口要成对**，而且**截断时才给**。

**「可达性」类**（触摸或读屏用户看不到、键盘会双触发）：

- **`title` 不是信息，是悬停。** 用户做决定必须知道的（花不花钱、为什么点不动）**必须有可见文字**；
  用例判据是这条信息能不能被 `getByText` 找到。
- **同一动作的鼠标路径与键盘路径各要一条用例。** 行内控件只 `stopPropagation` 了 click 是最常见的形状；
  修法是行处理器开头 `if (event.target !== event.currentTarget) return`，一行覆盖全部行内控件。

## 第 2 步：改实现

按项目既有写法改，沿用同族的先例。注释里写**为什么**（原来的写法会怎样错），不写「修了 bug」。

## 第 3 步：阳性对照（**最容易跳过、也最值钱的一步**）

**测试变绿不等于测试有效。** 一条永远为真的断言也是绿的。所以：

1. 把实现**临时退回缺陷版**（字符串替换，或 `git show HEAD:<path>` 取旧版）。
2. 跑新用例，确认它**真的会红**，而且**红在预期的那一句**上。
3. 恢复实现，复跑确认变绿。
4. **回读**文件确认恢复干净，再继续下一项。

它能抓到「我修错了地方」和「测试写得没意义」两类问题，产出的**实测数字**比任何形容词都有说服力。

## 第 4 步：按风险验证，复用项目入口

- 先跑能直接证明本次缺陷已修复的最小回归，再按影响面补检查：构建/类型改动验证构建与类型，交互/布局风险验证真实渲染，权限/支付等高风险链路另核对应行为与授权。
- 最终遵循项目已有的必需门禁、提交 hook 和 CI。hook 已跑同一套就不手动重复；本技能不要求把所有 test、lint、build、check 跑一遍，也不允许跳过项目必需检查。
- 同一代码版本、环境与判据下已有有效证据就引用；相关改动使证据失效时重跑受影响检查。
- 缺浏览器、账号、依赖或授权时，明确哪些结论未验证及是否阻断交付，不以模拟结果冒充通过，不为补证据擅自安装或执行外部写入。

### 回归优先；新增门禁按复发风险决定

修一个缺陷不等于必须新增脚本或 CI 门禁。先把最小回归接入现有合适的测试；仅当问题具有重复发生或跨多处影响的风险、判据可稳定二元判断、且收益高于维护成本时，再扩展为门禁，优先扩展已有检查。

无论采用哪一层，都保留红绿对照，确认检查会在已知缺陷上失败。

## 交付报告的三栏

**已实现 / 待核对 / 未执行**。三条硬规则：

- **编译或脚本通过 ≠ 视觉完成。** 分清「脚本绿」和「链路通」。
- 拿不到浏览器 / 账号 / 外部服务时**如实限定结论**，不把「未验证」写成「通过」。
- 每一项都要能回答「**哪个通道回读的**」。同一个工具既写又读，读出来的永远是它自己的信念。
