# 审计修复实例与坑（按需查阅）

本文件是 `audit-fix-loop/SKILL.md` 的披露参考：正文只留判断与步骤，这里留事故形状、实测读数和症状表。
**遇到对应分支时读对应一节**，不要默认通读。

## 1. 「前提本身不成立」的三种实例

- **推演的行为不存在**：报告说「界面容易让用户把停止理解成取消扣费任务」，但读文案发现按钮写的是「停止**回复**」、
  帮助行明说「不会撤销已产生的用量」——**这一条早就处理过了**。而它引用的那几行代码处**另有**一个真缺陷
  （忙时的悬停说明错用了删除按钮的理由）。**修在它指的位置，但按事实记账，不要把它描述的缺陷写进交付。**
- **交互推演被真实浏览器证伪**：报告说「label 里的链接会同时切换勾选」。真浏览器与 jsdom **双向都不切换**。
  这类「点一下会怎样」的断言**只有真浏览器算证据**；改为补一条回归测试钉住判据，**不改代码**。
- **建议的修复没有落点**：报告建议「按钮文案改为『停止等待 / 隐藏进度』」，但那一侧**根本没有停止入口**。
  要加就是新产品面 —— **不要为了让报告好看而发明一个入口**，如实写「建议无落点，待产品决定」。

另有一类：报告说「指标只数当前分页」，实现里其实已有截断判据与「只统计已加载的一页」那句，**缺的只是出口**。
先读全，再决定补什么。

## 2. 出口类缺陷的实测形状

- **出口必须对得上对账面。** 三个支付操作统一成「锁入口 + 说清原因 + 给出口」，但**充值/兑换的出口是交易记录，
  订阅不能去那里**（交易记录里只有充值，订阅不会出现）。阳性对照就把出口换成机械照抄那版，断言立刻红。
- **「有出口」与「出口真的通」在界面上长得一样** → 用例要数**请求数**。
- **说明与出口要成对**；而且**截断时才给**，没截断时给了会让人以为数字还漏了什么。
- 失败信息示例：导入重复 id 的断言 `expect(new Set(ids).size).toBe(3)`，失败信息是 `expected 2 to be 3`
  —— 一眼看出「丢了一件作品」。

## 3. 会伪装成代码缺陷的环境坑（每一条都实测踩过）

| 症状 | 真实原因 | 判据 |
|---|---|---|
| 浏览器探针报某条私有路由「未验证 / 元素很少」 | **限流额度被打满**（多个脚本共用同一份额度） | 页面里有没有「无法确认登录状态 / 稍后重试」那类文案。有 → 先清窗口，别改代码 |
| 清了服务端限流键，下一次请求**仍然**被挡 | 还有一层**浏览器侧冷却**（localStorage，跨标签页生效） | 两段都要清：服务端命名空间 + localStorage 里那个 cooldown 键 |
| 只改清单或只改代码，门禁两边都红 | 门禁是双向的：清单过期与实现缺失都会报 | 补哪边取决于「这个机制该不该在这一页」 |
| 登录接口稳定返回 **409**，界面提示是个没信息量的英文词（`Conflict`） | **账号并发会话数到顶**；`message` 是 `http.StatusText` 的状态词 | 判据只能落在 `code` 上（如 `AUTH_SESSION_LIMIT`）；前端丢掉 `code` 本身就是个真缺陷 |
| 脚本说「没写进剪贴板」，同一条探针在别的脚本里读得回 | **授权命令授错了浏览器上下文**：`Browser.grantPermissions` 不带 `browserContextId` 时授给默认上下文 | 授权类命令都带上会话的 `browserContextId`；同一命令两处结果不同先查运行环境 |
| 测试**全绿**，输出里夹着 `TypeError: div.scrollTo is not a function` | jsdom 只补了 `window.scrollTo`，没补元素上的 | **「绿着但有噪音」比红更危险**；跑完看未处理错误那一段，setup 里桩掉 `Element.prototype.scrollTo` |
| 量布局时页面老是「元素没渲染出来」 | 每次 `Page.navigate` 都消耗一次刷新额度 | **只导航一次，之后只改视口尺寸**；先打印 `document.body.innerText` 判断是不是限流 |
| 用户报「某某失效了」，而 diff 没碰过那条通路 | 需要先量「它本该有东西可动吗」 | 三问：①它本该动吗（量 `scrollHeight`/`clientHeight`）②diff 碰过这条通路吗 ③都不成立 → 优先怀疑陈旧模块/缓存/限流 |

**只清窗口，不改配置。** 为了本地方便去放宽限流或删掉冷却机制，是另一类缺陷。

## 4. 验证脚本自己也可能在骗你

| 症状 | 真实原因 | 判据 |
|---|---|---|
| 脚本连点「查询」重试 6 轮都等不到刚写入的数据，而直接查库证明数据已落库 | 重试只做了「应用筛选」：筛选条件没变 → query key 不变 → 数据层直接回缓存，**一次请求都不发** | **重试前后要看请求数有没有变**。「重试没成功」与「重试根本没生效」在界面上长得一样 |

同族提醒：断言要落在**业务结果**上（列表条数、文案），不能停在「我派发了事件 / 我调了接口」。
「接口 200」只证明后端给了数据，证明不了**那个按钮把它交给了用户**——按钮里往往还有第二步。

## 5. 三个编辑陷阱

1. **同一批里发两个并行 Edit，可能有一个报成功但没落盘。** 判据：返回 success 之后**仍然 grep 回读**。改成串行发。
2. **文件被长跑的 watcher 锁住时报 `EBUSY`。** 等一拍重发即可，不要换工具绕。
3. **同一条 shell 命令可能被执行两次** —— 最阴的一个，因为它会污染阳性对照的备份：第一次成功（改文件 + `cp` 备份），
   第二次 `cp` 先跑（把已改过的文件备份下来）、断言才失败，于是「恢复」恢复出**缺陷代码**。判据与做法：
   - 备份**在确认断言会通过之后再取**，或让备份名带内容指纹（`git hash-object <file>`）；
   - **恢复前先核验备份里有修复版的标记串**；
   - 「断言失败但文件确实变了」这种自相矛盾 → **先怀疑命令被执行了多次**；
   - 同源：**heredoc 里的中文长行**在重跑下会被截断，报 `SyntaxError: unterminated string literal`。
     **长文本一律走「写文件 + 读取追加」，不走 heredoc。**
