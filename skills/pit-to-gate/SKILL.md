# 把经验变成可验证约束

目标是降低已知失败模式的复发概率。门禁、skill 和文档都有覆盖边界，也都可能过时。

## 1. 确认值得保留的经验

先找本次真实失败的证据：复现输入、失败输出、事故记录，或反复出现的评审意见与返工。写清症状、根因和影响范围。

只有未来会影响决策、且代码或现有文档没有充分表达的经验才需要落盘。已有载体优先更新；没有新增经验时可以不修改文件。普通任务完成不等于必须新增 skill 或门禁。

已有文字说明不替代机器约束；已发生的失败仍缺可验证检查时，继续按下方路由判断并补齐合适载体。

完成判据：能指出失败证据及复用价值；证据不足则说明缺口，不据此新增强制规则。

## 2. 选择最小载体

先查当前项目和技能库中的已有约束，再按下表分流。一次经验可能拆成机器可判定部分与人工判断部分，避免重复维护同一规则。

| 判断 | 落点 | 完成判据 |
|---|---|---|
| 能把输入、预期和失败信号明确编码，稳定区分允许与违规情况 | 已有检查、测试或新的门禁 | 已知坏例失败、合法例通过，真实执行入口会报告失败 |
| 仍需判断，但取证步骤、分支和停止条件可复用 | 已有或新的 skill | 触发条件明确，步骤能走通，结论附可核对的证据 |
| 是项目事实、设计理由或有用的例外背景 | 项目现有记忆或文档 | 说明结论、原因、影响范围与失效条件，避免复制配置即可查到的内容 |

记忆系统自动抽取的经验或案例记录只算提醒与参考，不是机器门禁也不是 skill；要防重犯，仍必须落到门禁或 skill，不能因为已经自动记下来就跳过分流。

skill 可以由用户点名，也可在运行环境支持时按触发条件自动加载；实际生效取决于加载机制和执行证据。门禁只有接入实际会运行的入口后，才具备自动拦截作用。

## 3. 实现机器门禁

### 定义边界

- 写清约束、真实失败出处，以及允许和禁止的最小例子；注释或测试引用可定位的证据。
- 先覆盖已知失败模式，明确暂未覆盖的边界。规则无法区分合法与违规情况时，回到取证或 skill 分支。
- 从项目现有脚本、测试配置和 CI 查询接线方式，不套用固定文件名、脚本名或检查清单。

### 区分「提醒」与「门禁」

- **只提醒不失败的工具不是门禁**，哪怕阈值、文案、文档位置都写对了。实测：某仓库一个工具从
  2026-09-17 起就在超长时打警告（阈值 120 行），规则同时写在三处文档里，**但它退 0**；
  两周多后被它盯着的对象长到 **569 行（原上限的 4.7 倍）**，每次开工吐出 104 KB ——
  **全程没有任何东西会失败**。⇒ 规则要落成门禁，就必须有一个会变红的信号。
- **别去改那个「只提醒」的工具来加失败**：它往往同时是给人读的入口，拦住开工是另一个问题。
  另起一个检查脚本退 1，两者分工写进注释（一个给人读、一个挡回归）。
- **阈值与边界只能有一份来源。** 多个消费者各写一份 `120` 一定会漂，漂成「A 说超了、B 说没超」
  —— 这种状态谁也说不清，而且两边都还是绿的。抽成一个小模块供两边 import，并加一条断言：
  **两边对同一输入报出的数字逐字相同**。
- **阳性对照要有一条走真实入口**：夹具测的是逻辑，真实文件那条测的是接线。做法是往真文件里
  临时注入违规内容 → 确认门禁非零退出、且所有消费者报出**同一个**数 → 还原 → 复量回到合规。

### 修复挂在「只在某个环境里存在的机制」上时：另立一条环境假设门禁

判据：**这个修复要生效，依赖某个在单测环境里根本不存在的机制吗？**

实测（2026-09-27）：画布节点的失败面完全挂在 `<video onError>` 上，而 **jsdom 不加载媒体** ——
`error` / `loadedmetadata` / `readyState` 一个都不存在。于是单测只能用手工 `fireEvent.error` 验**排版**，
**证明不了真的会有人来触发它**。这类缺陷的正确载体是两条，缺一条都不完整：

1. **单测**：验排版与分支（含「播放器已经消失」这种强断言，不只断言文案出现）。
2. **真浏览器门禁**：钉住那个**环境假设本身**，并同时给出**阴性对照** ——
   假设成立时（坏源 ⇒ `error` + `readyState === 0`）与假设不成立时（真能播的源 ⇒ 不抛 `error`）都要量。
   ⚠️ 阴性对照要**自己产**（本仓用 `MediaRecorder` + `canvas.captureStream()` 现产 webm、
   页面里现合成 WAV），**不引二进制 fixture** —— 有了 fixture 就得维护它，而它跟被测行为无关。
3. 量环境读数时，**取事件当刻的值，不是事后某个时刻的**。事后读会在「元素停在哪就是哪」这个假设上偷懒，
   而守卫读的正是事件当刻的值。

⚠️ 这类门禁还有一个附带收益：它能钉住**事故的机制**而不只是修复。本仓那条顺带断言
「同源未知路径必须回 `200` + `text/html`」—— 哪天有人把它改成真 404，门禁会红并提示「事故形状变了」，
而不是让一个已经不再触发的守卫继续绿着。

### 验证好坏对照

1. 用最小坏例验证规则确实失败，再用合法例验证通过；包含容易被误报的必要边界。
2. **还原旧实现做阳性对照时，必须还原「调用点语义」，不是只换谓词。** 实测（2026-09-27）：旧代码是
   `if !c.GetBool("use_access_token") { setupPlaygroundToken(...) }` —— 谓词在该路由上恒为真，语义是
   **「永不跳过」**。若把判据还原成 `if !c.GetBool("use_access_token") { return nil }`：谓词一样、
   **分支语义相反** ⇒ 测试照绿，得到一个**假阳性对照**。忠实还原后四条断言当场全红。
   判据：还原后必须**变红**，且失败信息要落在被测行为上（那次应是 `token_name: real-api-token → playground-default`）。
   **「测试还是绿的」先怀疑对照写错，别急着当成「改动与缺陷无关」。**
3. 验证真实执行入口的扫描范围、配置、工作目录和退出码。优先在临时目录或隔离检出中放入已知违规，通过项目实际使用的命令确认非零退出，再恢复合法状态确认零退出。
4. 若入口支持临时 fixture，仍要核对真实项目中的目标路径没有被过滤掉；只测纯函数不能证明扫描和接线正确。检查测试输出包含预期用例，防止测试进程提前退出造成假绿。
5. 恢复临时改动并清理产物，保留用户原有改动。记录实际命令及结果；真实入口未验证时明确剩余缺口。

### 判据必须与真实链路同源

**两种常见的「假绿」**：

1. **自证循环**：测试里的「预期值」是从被测实现反推出来的常量，于是怎么改都相等。
   实测（2026-11-07）：不亏本测试用 `售价 / 1.4 / 7.2` 当成本，再比 `售价 ≥ 成本 × 1.15` ——
   倍率恒等于 `1.4×7.2/7.5 = 1.344x`，**把加价退成 0 之后测试仍然全绿**。
   判据：把被测逻辑临时改成「什么都不做」，测试必须红；不红就说明预期值是实现自己算出来的。
   修法：预期值要有**独立来源**（上游价目页、实测扣费凭据、手算常数），不从被测函数反推；
   再加一条结构性断言（如「参考图加价部分自身回本」），两条判据同时成立才算数。

2. **绕过真实调用顺序**：测试直接调内部函数，跳过了真实入口的前置步骤。
   实测（2026-11-07）：分辨率校验的单测全绿，线上却「0.5k 被静默归一成 1k 后才报错」——
   因为 handler 里先归一化再校验，而单测直接调了校验函数，绕开了顺序。
   判据：**一个校验的测试如果不经过真实的 handler/路由链路，它只证明「函数单独能跑」，不证明「线上会拦住」**。
   修法：至少一条用例走真实入口（或最小可复现的 handler 链），并对已知坏输入断言**具体错误原文**。

### 保证可导入、可执行

- 将检查逻辑与扫描、打印、写文件、启动子进程等动作分开。供测试导入的模块在导入时不执行这些动作，也不结束调用进程。
- CLI 动作放到独立入口或使用运行时适用的入口守卫。Node.js 检查器在适当位置设置 `process.exitCode`，避免直接退出截断输出或测试。
- 接入项目真正使用的验证命令或 CI，并确认上层命令传递失败退出码；脚本文件存在不代表已接入。
- 所需环境缺失时显式报告“未运行”或失败，按项目约定处理；不把跳过当作已验证。CI 具备浏览器、受控服务等前置条件时，同样可以运行对应检查。
- 豁免项写明理由与移除条件；能机器判定过期的豁免，加入反向检查，要求及时移除。

完成判据：好坏对照有效、真实入口和失败退出码已确认、导入无意外动作，接线与必要前置条件可核对。

## 4. 落为 skill 或项目记忆

- skill 保留触发条件、前置证据、决策分支、操作步骤、完成判据和失效条件。用本次案例走通流程；涉及命令时核对工具存在及参数适用性。
- 项目记忆沿用项目既有文档分工，只留未来决策需要的原因和限制；事实已有权威来源时使用带适用条件的指针。
- 更新原结论，合并重复条目；步骤数、工具数量等可变统计由实际内容推导。
- 修改 skill 后按 `skill-maintenance` 验证 frontmatter、实际加载路径和有变化的索引；只修改授权范围内的资产。

完成判据：读者能判断何时使用、如何核验结论，以及何时应修订或删除这条经验。

## 5. 复审与交付

遇到误报、绕过、工具替换或适用对象消失时复审。合法行为被误拦就修正规则；前提失效就删除或收窄约束，同时检查入口和引用。

交付说明：失败模式、选择的载体和路径、验证命令或证据、剩余覆盖边界。没有落盘时说明没有新增可复用经验或证据尚不足。
