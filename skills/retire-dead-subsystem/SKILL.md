# 摘除一个死掉的子系统

用户说「弄掉那个依赖」「X 已经和项目没关系了」「把这批清掉」时用这套。

**核心分界：一个子系统里有两批东西，必须分开处理。**
- **硬依赖**：还挂在门禁 / CI / 构建里的那一条。先摘它——它决定了「这个子系统还算不算在流程里」。
- **休眠件**：脚本、npm 条目、快照文件、文档引用。它们不在任何检查里，**留着不影响任何检查，
  但会让后来的人以为这个子系统还在流程里**。这是第二批。

**先摘硬依赖，再清休眠件。** 顺序反了会白做一遍——硬依赖没了以后，休眠件里哪些其实还有活消费者，
才看得清。

## 1. 删之前：建反向引用表（最容易做错的一步）

**按 import 边查，不按文件名筛。** 按文件名筛必然漏，实例：清一批设计工具同步脚本时，
按前缀筛得出「7 个文件、已无调用方」——实测 11 个，且共享库有 6 个消费者，
其中两个（`canvas-spec.mjs` / `measure-controls.mjs`）**名字里根本没有该工具名**；
`canvas-spec` 还另有一条下游（`spec-diff.mjs` 消费它的产出）。

```bash
# 对每个候选文件，查谁引用它
grep -rn "from '\./<文件名>.mjs'" scripts/ src/
# 更宽一点：查名字出现过的地方（会带出注释引用，人工分辨）
grep -rl "<文件名>" scripts/ src/ docs/
```

产出两张清单：
- **零消费者** → 可删。
- **有消费者** → 逐个看消费者自己是活的还是也是休眠件；**成链的要么整链删，要么整链留**。
  实例：`canvas-spec → spec-diff` 是一条链，浏览器侧另一半是 `page-spec-probe` /
  `page-spec-capture`。整条链的基线是外部工具，工具没了，链整体失效。

**顺手会捞到早已孤儿的文件**（实例：`spec-sink.mjs`，唯一提及它的是另一个脚本的一句注释）。
一并处理，但要向用户说明「这比原先报的多了 N 个」。

## 2. 删的动作清单

按这五项逐项做完，缺一项就留悬空引用：

1. **文件**：`git rm <...>`（不要 `rm`——要能 `git show <sha>:<路径>` 取回）。
2. **npm 脚本项**：删完**机械核一遍没有脚本项指向不存在的文件**：
   ```bash
   node -e "const p=require('./package.json'),fs=require('fs');
   for(const[k,v]of Object.entries(p.scripts)){
     for(const f of (v.match(/scripts\/[\w.-]+/g)||[])) if(!fs.existsSync(f)) console.log('✗',k,'->',f)}"
   ```
3. **快照 / 生成物**（`*.json` 之类）：连同**读它的那个脚本**一起删，否则会留一个没有读者的数据文件。
4. **CI 与门禁**：如果它挂在 CI 上，连同那个 step 一起删。**「环境不具备就跳过」的 step 必须删**——
   一条在 CI 上永远不可能成立的门禁，等于把「跳过」伪装成「通过」。
5. **文档与注释**：见第 3、4 节。

## 3. 搬 md：链接基准陷阱

把 md 搬进 `archive/` 或改目录时，**内容一字未改也会坏掉别处的链接**——坏的是解析基准。

- 实例：一处 `docs/DESIGN-SPEC.md` → `docs/archive/DESIGN-SPEC.md` 的搬移，连带坏掉 **3 条别处的**链接
  （别的文档里指向它的、以及它自己指向 `docs/prompts/` 而非 `docs/archive/prompts/` 的）。
- **`check:doc-links` 要跑两遍**：第一遍暴露没预料的连带项，第二遍确认修对了。
- **基准要按「从哪一层数」重算，不要凭感觉**：`docs/archive/prompts/README.md` 到仓库根的
  `AGENTS.md` 是 `../../../AGENTS.md`，不是 `../../AGENTS.md`。
- 「逐行校验内容一字未改」**查不出这一类**，只有链接检查能。

## 4. 判据不跟着工具删

工具删了，**教训要留**。删之前先问每一份文档 / 注释：

- **这条是「怎么用那个工具」还是「那个工具教会我的判据」？** 后者要留。
  实例：「工具报成功不等于真的成功，必须回读」「一个恒为 0 的读数与『真的没有』在输出上同形」
  「任何『真值 → 外部系统的投影』都需要一个机械对账入口」「改完等热更新落地再采」——
  换成任何外部通道都成立。
- **整节加历史边界，不重写正文**：节首写清「工具已删 / 现在按历史读 / 保留的理由是 X /
  要重建用 `git show <sha>:<路径>`」。归档正文按原样留，已知被推翻的结论在节首点一句。
- **源码注释里「实测值 32px」「对应 XX 组件」这类取值依据不删**——删了后来的人不知道那个数字为什么是它。

## 5. 连带计数会变

删文件会改变文档里记着的读数（扫描文件数、按某属性选元素的脚本数、门禁条数）。
**逐项复量，不要凭减法学**：

- 实例：`check:secrets` 从 725 → **708** 文件（差的 17 = 前一轮删的 1 个 + 这一轮 16 个）。
- 实例：「按 `data-design-key` 选元素的脚本」从 9 → **6**——因为删掉的三个也按它选元素，
  而这条名单写在三份文档里（AGENTS / STATE / FIELDS），三份都要改。
- 计数一律写成「**实测值 + 日期**」，并说明与旧值的差从哪来。

## 6. 收尾验证

**跑项目规则文件（AGENTS.md、CLAUDE.md 等）声明的那套门禁入口**，按改动面选档，不照抄固定命令表：

```text
<项目声明的门禁入口>        # 例子：npm run check:quick / npm run ci:local / npm test && npm run lint
```

这一步必须证明的是：**删掉的东西没有被任何活入口引用** —— 那条引用检查真的跑了，而且它在坏输入上会红。
项目没有统一入口时，按删除面逐项列出跑过的命令与退出码，别只说「跑过了」。

- 只删脚本 / 改注释 / 改文档时，**运行时门禁（要 dev server 的那些）可以如实记「未执行」**，
  但要写清理由：本轮未动运行时行为。
- 构建因环境或安全策略拒绝清理而失败时（批量删除被拦、临时目录被占用），**保留错误与旧产物、报阻塞**；
  不通过换输出目录绕过拒绝。拿到可执行的清理授权或环境调整后再构建，并重新验证退出码与产物。
- 报告分三栏：已实现 / 待核对 / 未执行。**别把「脚本绿」写成「页面完成」。**

## 7. 三个真实踩过的坑

1. **对同一个文件并行发两条 Edit，第一条会被第二条覆盖**——两条都回「成功」，
   实际没落盘。**同一文件的多处修改必须串行**；回读换独立通道（`git show HEAD:<path>` / `sed -n 'Np'`）。
2. **提交信息里的否定式断言（「已无调用方」「已无引用」）必须由一次机械 grep 支撑**——
   凭印象写会差一个数量级。写错了就 `git commit --amend -F <msgfile>` 改掉（本地未 push 时安全），
   并在正文里写明「原提交信息此处不准，实测更正如下」。
3. **用户说「那个依赖」（单数）时，不要顺手扩大范围。** 先摘那一件，把剩下的盘点清楚，
   **带着推荐**问要不要继续清（推荐要说明代价：会失去什么能力、能不能从 git 取回）。
