# 文档漂移审计

用户说「清理整理文档」「看看有没有漂移的」「归档当前内容」时用这套。

**核心分界：文档漂移不是「写错了」，是「曾经写对了」。** 所以判据不是「读起来对不对」，
而是**拿一个当前的真值去对**。没有真值的断言不要动它——那是文风问题，不是漂移。

## 四类漂移（按危害排序，第 1 类最重要）

### 1. 前提本身不成立

待办的目标对象已经不存在了，条目却还在。**它读起来完全正常，所以最难发现。**

判据：**问「这条待办的宾语还在吗」。**

实例：某条 OPEN-ISSUES 叫「新增控件尚未与设计稿主件同步」，而设计稿流程本身已停用
——目标对象没有了。处置不是「标记已完成」，是**「已撤销：不需要做」**，并写明
设计真值现在在哪。同类还有：整篇以某个已停用流程为框架的文档（加顶部边界，别重写正文）、
决策台账里以旧对象为验收标准的「硬前置条件」（逐行加失效标记）。

### 2. 悬空引用

注释或文档引用一份不存在的文件。**先别急着改注释——大概率能从 git 历史恢复。**

```bash
# 找历史上存在过的文件
git log --all --pretty=format: --name-only | sort -u | grep -i "<关键词>"
# 找到删除它的提交
git log --all --oneline --diff-filter=D -- <路径>
# 取删除前的内容
git show "<删除提交>^:<路径>"
```

恢复后**逐条回代码核实**，不要照注释转述——实测中恢复出的 9 条里有 1 条已被后续批次推翻，
照转述就会写错。恢复出来的内容放回它该在的现役文档（如 `MOTION.md`），并注明恢复来源。

### 3. 状态断言过期

「未开工 / 待实现 / 计划中」这类。**去代码里找唯一真值对**，不要相信文档间的互引。

判据示例：`PAGE_STATUS`（路由表）、`package.json` 的 scripts、文件是否存在。
实测抓到一条「代码未开工（2026-09-15）」，而对应文件已存在、状态是 `ready`。

### 4. 计数型描述失效

「为什么是这五条」「8 个区块」「三个来源」——**增删一次就失效，而且没人会回去改**。

处置：**改成写「收录判据」而不是写条数**。如「为什么是这五条，不多不少」→
「收录判据：在干净检出上可重复、且不需要外部依赖」。

**特别容易漏的一类：检查器自己的输出计数。** 文档里写「`check:doc-links` 138 条链接 · 0 断链」
——那个 138 **每改一次文档就变**，是所有计数里漂移最快的（实测同一份文档同一天：
92 → 142 → 147 → 150，改四轮涨四轮）。这类**不要改成「实测值 + 日期」，直接删掉数字**，
判据只留「0 断链」——因为读者要的从来不是条数，是「有没有坏的」。

**但要先分清两种计数。** 上面那种（检查器输出）读者不需要数字，删。
另一种是**修辞型计数**——数字本身是论据，删了句子就没了意思。
实测：README 写「7 个脚本已经共用那套 CDP 客户端——再引一套就是两套浏览器栈做同一件事」，
实测是 **19**；而同一份 README 另一处写「被 10 个脚本 import」，**两处还互相矛盾**。
这里的「很多」才是论点 ⇒ **保留数字、改成复量值 + 日期**（「2026-09-20 实测 19 个」），
并且**同一事实只写一处**——两处各写一个数就是两个都会烂的副本。

**数完别忘了报「查过但没漂移」的那几项。** 审计报告只列找到的问题，读的人会以为其余没查。
实测一轮里查了 6 类、只有 2 处真漂移（脚本表差集为空、手抄色值 17 个全命中、
CI 步数三处自洽、测试计数 146/1787 一致、审计报告边界已标好）——**这些「无漂移」也要写进
提交信息与报告**，否则下一次还会有人从头重查一遍。

## 链接检查：AGENTS 里常写着要查，但仓库里往往没有工具

先确认有没有现成脚本（`grep -l "doc-links\|link-check" scripts/`）。没有就写一个，
判据是两件事：相对链接的目标文件是否存在、`#anchor` 是否真的存在。

**三个必须做对的点：**

- **跨仓库绝对路径要单独算，不能算死链。** 文档里常引用另一棵树的源码行号
  （`/path/to/other-repo/src/x.ts:155`），按相对路径解析全是误报。
  末尾的 `:行号` 是引用标注，解析前要剥掉。
- **失败必须退出 1**，否则当不了门禁。
- **别在文档里裸写示例链接** —— 纯文本检查器分不清「真链接」与「正文里裸写的例子」。
  实测：往 GOTCHAS 里补一条讲「搬移 md 会让链接基准漂移」的坑，正文顺手写了
  `[X](./Y.md)` 当例子，未剥离代码段的 `check:doc-links` 立刻红，报的就是那个例子。
  **举例要用反引号包住、或改写成纯描述**（「链接里的 `./` 前缀」而不是裸写出链接本身）。

### 阳性对照是必须的，不是可选的

一个恒绿的检查器比没有更糟。造一个坏文件链接 + 一个坏锚点，确认两条都被报出。

**退出码要单独确认，不要经过管道**——`npm run check:doc-links | tail` 拿到的
是 `tail` 的退出码，永远是 0。这一步真实骗过人：

```bash
<项目声明的链接检查入口> > /dev/null 2>&1; echo "退出码 = $?"
# 实例：node scripts/check-doc-links.mjs
```

## 归档时的链接基准陷阱（本条最容易被忽略）

**把 md 内容整段搬到另一个目录，内容可以一字未改，但相对链接全废**——
解析基准跟着文件位置变了（`docs/` → `docs/archive/` 差一层）。

**「逐行校验内容一字未改」查不出这一类。** 内容确实没改，坏的是基准。

所以搬运的验收要**分两条判据**，不能只做第一条：

1. **内容保真**：移走的每一行都能在目标里按序找到（逐行比对，不是比行数）
2. **引用可达**：按新位置重新解析一遍链接（跑项目声明的文档链接检查；实例：`npm run check:doc-links`）

修法是**按新位置重定基准**（`./` → `../`），不是把内容改回去。
如果归档头写着「内容未改动」，改完 href 要**如实补上这个例外**，否则那句就变假了。

**会不会断链，取决于搬的内容里有没有 markdown 链接**，不取决于搬了多少行。
实测两次：一次搬 103 行断 4 条（内容里有 `[文字](./X.md)`），
一次搬 97 行 0 条（路径全是反引号文本 `` `docs/x.md` ``，不构成链接）。
所以搬之前先 `grep -o '\[[^]]*\]([^)]*)'` 数一下，有链接就必须跑检查器。

## 归档前先读文档自己的「不许动」标记

**压缩/归档的规则可能和文档内部的显式禁令直接冲突，而冲突只有读了才知道。**

实测：`next.mjs` 的规则是「『当前动作』只该放当前这一条，更早的移到 `docs/archive/`」，
阈值 120 行、实测 420 行——**规则完全成立**。但那一节中间嵌着一条 ⚠️：

> 下面的「无限画布迁移」「全站动效统一」「AI 创作工作区」不是已结案的历史批次
> ——它们是同一件事的三个切面。**不要把它们归档、不要按「已完成的批次」读。**

那条 ⚠️ 保护的正是规则要求搬走的东西。**解法是让 ⚠️ 和它保护的几节一起留在原处**，
不是按规则搬走——按规则搬的后果是「把人类正在做的事标成已结案」，而工具会一路绿。

同类要留的还有**导航段**（「交接入口：选任务从 X / Y 进入」）——它是指路，不是某一轮的记录，
归档了等于把入口一起收走。

⇒ **搬之前通读一遍要搬的区间，找 `⚠️` / 「不要」「禁止」「不是待办」这类词**，
不要只按标题和行号切。

## 内部指针：落点搬了，指针没跟着改

除了「引用不存在的文件」，还有两类**指向文档内部**的指针，它们**不产生断链、任何检查器都看不见**：

1. **指向某一节的指针**（「见『当前动作』」「见下节」）。实测：两张表写着「加载态与空/错态未在
   浏览器实测，见『当前动作』」，而那段正文**三天前就归档进 `docs/archive/STATE-log-2026-09.md`**
   ——指针原地不动，读者照它去翻只会扑空。**修法是按新落点重指，并且用节名而不是行号。**
2. **行号型指针**（「见本文件第 7 行说明」）。**任何一次插入都会让它失效**，而且失效后
   指向的往往是一句无关的话，读起来毫无异常。⇒ 见到就改成节名/标题文字。

**归档时的连带动作**：搬完在**其他文档**里 `grep` 一遍被搬走的节名与小标题
（`grep -rn '当前动作\|见下节' docs/*.md`），确认没有指针还指着已搬走的落点。

## 交叉核对不只对代码，也要对文档自己

同一份文档内部会自相矛盾。实测抓到的例子：一张表写「账单 / 设置两页还没有画板」，
另一张表写「账单 7 张画板核对通过」——**两处都读起来正常，只有并排看才发现**。

所以除了「文档 vs 代码」，还要做一遍「文档 vs 文档」：
把同类断言（页面状态、数量、完成度）集中列出来互相印证。

## 归档本身：量的是出口，不是文件体积

判断「某份文档该不该归档」时，**量消费它的那条命令吐出多少**，不是 `wc -l` 文档本身。

```bash
<消费那份文档的命令> | wc -l   # 不是 wc -l <文档本身>
# 实例：node scripts/next.mjs，它吐「当前动作」那一节
```

真实数字差几十倍：某 180K 文档，取「当前动作」节的命令每次吐出 1836 行 / 167 KB，
因为历史条目全堆在那一节里，且**没有任何东西会报错**。

归档后必须复量同一个出口，确认降到阈值内。

**但「降到阈值内」只解决这一次。** 阈值本身要落成会失败的门禁，做法见 `pit-to-gate` 的
「区分『提醒』与『门禁』」——**只提醒不失败的规则等于没有规则**（实测：警告打了两周多，
对象仍长到上限的 4.7 倍，全程没有任何东西失败）。

## 「文档太长」的处置：先分清**入口文件**与**按需查文件**

用户说「这些文档太长了，整理一下」时，**不要一律去拆文件或压缩正文**。先分类：

| 类别 | 例子 | 成本模型 | 处置 |
|---|---|---|---|
| **入口文件** | `STATE.md`、`README.md` | 被**整份**读取或打印（`npm run next` 直接吐「当前动作」） | **压长度**：完成过程归档、只留进行中/下一步/阻塞/验收缺口 |
| **按需查文件** | `GOTCHAS` / `FIELDS` / `OPEN-ISSUES` / `VISUAL` / `BACKEND` | 一次只查**一节**（各自文首写着「只读本次相关章节」） | **冷热分离**：把**休眠内容的全文**外置，热路径只留判据与指针 |

⇒ **两类都不要「按节拆成多个文件」。** 节号是**引用契约**（实测：全仓 31 处引 `GOTCHAS` 第 6 节、
15 处第 7 节、11 处第 1 节），拆文件要改几十处引用与锚点；而一次查表本来只读一节，
**拆了不会让那一次更便宜**。

### 保留节号 = 零引用失效

外置某一节时，**原地留一个同号短节**（内容换成「仍然成立的判据」摘要 + 指向归档），
而不是把节删掉再重编号。判据是机械的：外置后把 `## 0.` ～ `## 9.` 逐个 `includes` 断言一遍。

⚠️ 顺带会捞到**本来就已经悬空**的引用。实测：两份源码注释都写「见 `GOTCHAS` 第 3 节**模式 A / 模式 B**」，
而「模式 A」「模式 B」在该文件里**一次都没出现过**（全仓 `grep` 只命中那两处注释）。
⇒ **搬之前先核一遍被搬内容里的引用**，这类悬空件平时没有任何东西会发现。

### 先量，再决定拆不拆

**体积最大的那份不一定该动。** 实测：`FIELDS` 98 KB 看着最吓人，但它 15 个页面节全是**实时契约**，
休眠内容（已停用设计工具的节点号）合计只 **396 B / 0.4%** ⇒ **决定不拆**，
理由写成「按页拆 15 个文件要改 44 处引用，而一次查表本来只读一节，成本大于收益」。

量的时候要量**冷内容**，不是文件总大小：

```bash
# 按节量字节（找出「一节吃掉 25% 文件」的那种）
node -e "const fs=require('fs'),t=fs.readFileSync(process.argv[1],'utf8').split(/\r?\n/),h=[];
t.forEach((l,i)=>{if(/^#{1,4} /.test(l))h.push([i,l])});h.push([t.length,'EOF']);
```

### 外置时的四个机械陷阱（都实际踩到过）

1. **工作树可能是 CRLF**（`core.autocrlf=true`；`git ls-files --eol <文件>` 报 `i/lf w/crlf`）。
   按 `\n` 切行再拼回去会把**整个文件**变成 diff。⇒ 切之前先 `includes('\r\n')` 探一次，
   全程用同一个 EOL 常量。**验收判据：`git diff --stat` 只有目标行变化。**
2. **相对链接的目标有三种，只改一层会漏掉第三种**：
   ① 还在同目录树下（`./reference/X.md` → `../reference/X.md`）；
   ② 已在目标目录里（`./archive/X.md` → `./X.md`）；
   ③ **在仓库根**（`../AGENTS.md`、`../src/…` → `../../AGENTS.md`、`../../src/…`）。
   ⚠️ **判据要写成「逐条把相对链接按新目录解析、断言目标文件存在」**，
   **不要写成「没有 `](./` 残留」**——后者会把合法的同目录链接（`](./DESIGN-SPEC.md)`）误报成漏改。
   实测漏的正是 ③，就是靠这条断言抓出来的。
3. **外置 ≠ 搬完就完**：`OPEN-ISSUES` 的派单表里有三处「见第 3 节」指向被搬走的条目，
   `grep '见第 N 节'` 才能发现。⇒ 搬完立刻 `grep` 一遍被搬走的节名/编号。
4. ⚠️ **用 `String.replace` 插正文时，`$` 有替换模式语义 —— 会静默把文档灌爆。**
   被插进来的正文里只要有 `` `$` ``（写价格、写 shell 变量、写正则都会碰到），
   序列 `` $` `` 就被解释成「**匹配之前的全部内容**」并原样插入；`$&`、`$'`、`$1`、`$$` 同理。
   实测（2026-09-25）：往 `FRONTEND-CUTOVER.md` 插一段含 `` `$` `` 的说明，
   383 行的文件一次写成 **547 行**，diff 从「+8 行」变成「+165 行」。
   ⇒ **替换值一律用函数形式** `src.replace(ANCHOR, () => block)`（没有解释层），
   并加两条断言：① 写回后行数只涨预期值；② 节标题/锚点只出现一次。
   **这类破坏不报错**，唯一的信号是「改动规模对不对」—— 所以每次写回后立刻看
   `git diff --numstat`，不对就 `git checkout -- <file>` 还原重来。

### 冷热分离的三档手法（按风险从低到高）

1. **纯子块外置**（最低风险）：原文自己就标着「历史取证 / 不是根因」的那种，父节留一句话结论 + 指针。
2. **已结案条目外置**：在节首留一张「结论 + 不重开的理由」表，原文（含反证、测量读数）进归档。
3. **休眠整节外置**：见上面的「保留节号」。

## 搬之前先复核被搬内容里的「状态断言」

搬移时你会逐行重读这些段落，而**「未发布 / 未验证 / 待观察 / 应该是 X」这类断言最容易在搬移之前
就已经过期** —— 它们写的时候是对的，之后被别的提交改掉了，**没有任何东西会因此变红**。

实测（2026-09-25 归档 STATE，20 节里抓到两条）：

- 一条写「（**未发布**）」，而 `git merge-base --is-ancestor <改动提交> <已发布提交>` 判 **yes** ⇒ 它早就上线了；
- 一条写「只能在远端 push 后看」，而 `gh run view <id> --json jobs` 已经能读到结论（`release = skipped`）。

**判据三条，都要过**：

1. 与发布记录交叉核对（`deploy/*.json`、发布文档的「当前正式版本」节）；
2. `git merge-base --is-ancestor` 判「这个改动在不在**已发布的那一版**里」——**别只看它进没进 main**；
3. 能远程读到的（CI 结论、部署 id）就直接读，别把「我没读过」写成「只能等以后看」。

⚠️ **发布记录本身也会错**：上面第二条的线索来自一份 release JSON，它的 note 写着「release job success」，
而 `gh` 读到的实际结论是 `skipped`。⇒ **一手读数优先于文档转述**，转述只当线索。

## 第三方工具产出的审计报告：存档 + 标边界，**不是**当成待办清单

项目里常躺着外部工具（或另一个 agent）生成的审计/评审报告。处置顺序：

1. **先看有没有重复。** 同名同 target、大小接近的两份，先 `diff` 全文。
   实测：两份**正文逐字节相同**，只差 frontmatter 两行（一份写「P1 6 项」、
   一份写「P1 7 项」）。数正文只有 6 条 ⇒ 前者自洽。**提交自洽那份，删重复那份**，
   删前逐行 diff 确认「重复文件里没有任何独有内容」。

2. **查它的第一条 P0 是不是已经修好了。** 报告越旧越可能已经解决。
   实测：审计写于 09-18 19:44，对应的修复提交在 **09-19 02:12**——
   **晚 6.5 小时**。P0 的内容与代码里那道闸门逐字对应。

3. **至少实测验证一条断言**，用来判断这份报告的可靠性。
   实测：某条 P1 断言「点 label 里的链接会同时切换勾选」——
   在真实浏览器里**被推翻**（点链接后 checkbox 不变）。
   **必须带对照**：点 label 纯文字会切换、点 checkbox 本体会切换，
   证明不是探针失效。原因写在规范里：label 的 activation behavior
   **不适用于交互内容后代**（`<a>`）。
   ⇒ 报告里其余条目**同样不能默认可信**。

4. **未验证的不进项目索引。** 项目的问题索引通常自己写着
   「先给可重复证据，确认后再加入本表」。未核实就登记 = 污染索引。

边界怎么写：审计时点 + 哪条已修（带提交号）+ 哪条被实测推翻（带实测值）+ 一句
「其余条目的断言一条都没核实过，要采纳先按 `文件:行号` 复现」。

## 边界：刻意不要动的

- **先查有没有脚本/源码按路径读它** —— 见下节，这条最容易翻车。
- **`archive/`、`prompts/` 是历史资料**——它们本来就不该与当前一致。
- **已有明确日期边界的快照**（「本文审计时点为 X、commit Y」）——边界够用就别动正文。
- **取值依据类注释**（「画板实测 32px」）——删了后来的人不知道为什么是这个值。
- **仍需要旧工具的脚本与条件步骤**（如某检查仍需连本机设计工具）——流程停用 ≠ 工具失效，
  要说清「哪一半仍成立」。
- **决策台账的历史条目**——历史保留、只加失效标记，不删。

## 移动或删除文档前：先查「谁按路径读它」

**这一步不能省。** 实测：某份文档已被标为「历史资料」，看起来该进 `archive/`，
但 `scripts/check-design-keys.mjs` 在**模块顶层** `readFileSync('docs/DESIGN-SPEC.md')`，
用正则读它里面的两张表。

```bash
# 用「文档名」而不是某一份的具体路径
grep -rn "<文档名>" scripts/ src/ --include=*.mjs --include=*.ts --include=*.tsx
```

**搬走它 = 脚本 `process.exit(2)`**。而 CI 往往把退 2 当「环境不具备 → 跳过」，
**只留一条 warning**——也就是 **CI 会安静地跳过这一步，和正常跳过在输出上一模一样**。

所以对这类文档，正确处置不是搬走，而是**在头部写明「哪一部分是活输入、为什么不能动」**：
「本文除 §N 的台账表外只作追溯用」。只写「余下内容只作追溯用」是**错的**，
后来的人照它删表，检查器就静默失效了。

**反向也要验**：改完这类文档的头部后，**跑一次那个脚本**，确认解析没被弄坏
（实测：改头部后 `check:design-keys` 仍读到台账 100 条）。

## 自称「滚动更新 / 持续维护」的节要单独查

它比别处更容易过期——因为读者会按「这是最新的」去理解。

实测抓到：某审计文档头部写着「历史快照，不是当前待办」，
**而里面有一节标题是「执行进度（滚动更新）」**——两句互相矛盾。
核对确认那节的「滚动」在某天之后就停了，里面有三处过期。

处置：在节首写明**冻结点**与当前进度的去处，把过期结论**就地标注**，
其余保持原样以留证据。

## 工具本身要先被验证（恒真/恒假的读数与「真的没有」同形）

检查器输出里出现**形态正常但恒定不变**的条目时，先怀疑检查器。

实测：某检查器的「未覆盖」列表第一条是字面量 `${designKey}`。根因是它用
`indexOf('data-design-key=')` 找声明，**不区分 JSX 属性还是字符串**——
而 `querySelector` 的选择器 `` `[data-design-key="${x}"] textarea` `` 也含这串字符。

它一直没被发现，是因为落在「已知、**不判失败**」的列表里，
而且**假条目和真条目长得一模一样**。

修法与纪律：
1. 加约束（如「要求前面是空白」——JSX 属性一定如此，选择器前面是 `[`）。
2. **改动前后逐项对比集合**，确认只少了假的那条、真的一条没动
   （实测 198 → 197，新增 0）。
3. 加一条**只提醒不失败**的自检（抽到含 `${` 的 key 就警告）。
4. 做**阳性对照**：把守卫摘掉重跑，确认警告真的会响。

## 交付形态

- 改**原位**，不要在文件末尾追加「第 N 轮修正」。删掉失效结论，别留两版。
- 把「已修复项」登记进项目**指定的防重复开发索引**（如 OPEN-ISSUES 的「已修复项」节），
  而不是新写一份审计报告——报告本身也会漂移。
- 提交分组：归档 / 新增工具 / 漂移修正 分开，便于回退。
  ⚠️ **但「文档里登记的文件」必须与文档同行提交**：如果 README 的脚本表里有一行指向某个
  `scripts/*.mjs`，而那个脚本**从未入库**，双向一致性检查会**两个方向都不自洽** ——
  先提交脚本（文档还没那一行）⇒ 反向「磁盘有、表里没有」红；先改文档（脚本未入库）⇒
  正向「表里有、磁盘没有」红。**唯一自洽的切法是把两者并入同一个提交**。
  ⚠️ 这类检查通常读**磁盘**（`readdirSync`）而不是 `git ls-files` ⇒ **本地过、CI 红**，
  而 `ALLOWED_MISSING` 一类的豁免表往往自带反向检查（「磁盘上存在 ⇒ 豁免过期」），
  走不通。2026-09-25 在 `web-console` 实际踩到（`clear-rate-limit.mjs`）。
- 最终报告分三栏：**已修 / 刻意未动（附理由）/ 待用户决定**。
